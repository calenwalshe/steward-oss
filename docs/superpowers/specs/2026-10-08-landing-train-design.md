# Landing Train — design

Date: 2026-10-08 · Status: approved in conversation (the owner), spec awaiting review

## Problem

Accepted Steward work does not reach `fleet-registry`. On 2026-10-08 ~00:10 the Steward repo held
6 ACCEPTED + 2 NEEDS_HUMAN + 4 RUNNING jobs unmerged, 37 `steward/*` branches ahead of
`fleet-registry`, 15 of them "Merge `fleet-registry` into YOUR branch" fix-up jobs. Causes, from
the event log and the 2026-10-06/07 manual drains:

1. **Fix-up cascade.** Jobs land one at a time. Each landing moves `fleet-registry`; the next job
   conflicts in the same hot files (`runner.py`, `cli.py`, `check_runs.py`, golden fixtures);
   Steward spawns a full worker job to resolve it (~30 min); `fleet-registry` moves again; repeat.
2. **Stale `.git/index.lock`.** Tests and git run inside the deploy checkout. When one dies the
   lock stays and every merge blocks until a human removes it (12:12→06:57 on 2026-10-07;
   again 00:03 on 2026-10-08).
3. **Gates that misfire.** Tech-lead review allowance runs out; the test-weakening check compares
   a fix-up branch with its own history and flags merges as test removal (1b441f50, false positive).

## Goal and success criteria

Everything landable lands without the owner: by morning, every ACCEPTED Steward job is merged into
`fleet-registry`, deployed and healthy, or listed in a morning report with the reason it could not land.

- Zero-touch: no human action needed for any job that can land.
- Speed: a queued job lands within one train cycle (minutes), not ~30 min per job.
- Nothing unlandable blocks anything else.

## Decisions (the owner, 2026-10-08)

| Question | Decision |
|---|---|
| Speed vs zero-touch | Both. |
| Resolver authority | **Full resolver**: an AI resolver fixes real conflicts unattended; a train lands only if the full suite is green and no tests were removed. |
| Cadence | **Continuous**: a train every ~3 minutes when the queue is non-empty. |
| Housekeeping | Auto: clear stale lock, stop superseded fix-ups, release landed jobs, stop spawning per-job merge fix-ups, archive orphan branches (rename, never delete). Never: delete branches, rewrite history, push. |
| NEEDS_HUMAN jobs | Stay the owner's. The train lands ACCEPTED jobs only. |
| Scope | Steward repo (`fleet-registry`) first. Other repos later, same mechanism. |

## Architecture

```
accepted jobs ──► Landing queue (DB table, FIFO by accept time)
                        │ every ~3 min, if queue non-empty & merge lock free
                        ▼
              Train builder  (dedicated worktree ~/.cache/steward-merge/train,
                              never the deploy checkout)
                 1. branch train/<n> from fleet-registry
                 2. merge each queued job; on conflict → Resolver (one per train)
                 3. gates (below)
                 4. red? bisect: drop the culprit job(s), retry the rest
                        │ green
                        ▼
              Land: flock(merge lock) + ff-only fleet-registry → deploy-self → health
                        │
                        ▼
              Release landed jobs · stop superseded fix-ups · clear stale locks
              Dropped jobs → morning report (+ one tg notice)
```

Replaces: the one-at-a-time delivery-worker incorporate path, and the per-job
"Merge `fleet-registry` into YOUR branch" fix-up jobs.

## Components

**Landing queue.** A store table: job id, branch head, accepted_at, attempts, last_drop_reason.
A job enters on ACCEPTED (and the current ACCEPTED backlog is enqueued once at rollout). It leaves
on land (→ RELEASED) or after 3 drops (→ stays ACCEPTED, flagged "needs you" in the report).

**Train builder.** Runs from the control loop on a ~3 min tick. Holds the existing merge lock
(`steward/incorporate.py target_lock()`) only for the final ff-only landing, not while testing.
All git and pytest work happens in the dedicated train worktree with `TMPDIR` under
`~/.cache/steward-merge` (never `/tmp`, a 15 GB quota tmpfs).

**Resolver.** An Opus worker, started only when a train has conflicts. Input: conflicted files,
each job's goal and diff. Rules: keep both sides' intent; never revert `fleet-registry` refactors;
golden fixtures (`misc_text.golden.json` and similar) are regenerated by their own test, never
hand-merged. 20 min budget per train; on timeout the job with the most conflicted hunks is dropped
and the train retries without it.

**Gates (all must pass before landing).**
1. Full suite under pytest-xdist on the merged train tree.
2. No test function or assertion removed versus the train's base (`fleet-registry` at train start),
   measured on the merged tree, not on any job branch.
3. After deploy: import smoke and `steward health`.

**Failure handling.**
- Red suite: bisect the batch (halve, retry each half) until the culprit set is isolated; land the rest.
- Bad deploy (health fails after landing): revert the train's merge commit with a new commit
  (no reset), redeploy, report.
- Stale `.git/index.lock` in the deploy checkout: older than 5 min and no live git process → remove
  and log.

**Housekeeping (each cycle).** Release jobs whose work is merged and deployed. Stop fix-up jobs whose
parent has landed. Rename orphan `steward/*` branches with no job record to `archive/steward/*`.

**Morning report.** Written to a file and sent as one tg notice: trains run, jobs landed (commits),
jobs dropped with reason, suite counts, locks cleared.

## Out of scope

- Other repos (steward-android, plan-tracks, music lab, ...): same mechanism later.
- Auto-accepting NEEDS_HUMAN jobs.
- Pushing to any remote.

## Testing

- Unit: queue transitions; bisect on a synthetic batch with one bad job; the test-removal gate on a
  merged tree (including the 1b441f50 shape: must pass); stale-lock rule (age + no process).
- Integration: a throwaway repo with three branches that conflict pairwise, one that breaks a test,
  one that is clean → the train lands the clean and resolvable ones, drops the breaker, report lists it.
- Prove live: drain the current Steward backlog through the train; every ACCEPTED job either lands
  or appears in the report with a reason.
